# 분야별 리뷰 지침

각 에이전트는 자신의 분야만 맡는다. 제공된 요구사항과 변경 전후 코드를 근거로 검토하며
읽기 전용으로 작업한다. 관련 코드는 읽어도 되지만 저장소 전체의 기존 문제를 나열하지 않는다.
각 지적은 실제 파일 위치, 발생 조건, 영향, 권장 수정으로 뒷받침한다.

## comments — 주석 정확성

- 수정된 구현 주변의 기존 주석과 docstring도 읽는다. 설명 대상 동작이 달라졌는지 확인한다.
- 반환값, 예외, 단위, 기본값, 부작용, 동시성, 캐시 조건에 관한 설명을 실제 코드와 비교한다.
- TODO와 비활성화된 코드가 현재 의도에 반하거나 잘못된 설명을 유지하는지 확인한다.
- 주석의 개수나 문체 자체를 결함으로 삼지 않는다. 잘못된 설명이 유발하는 오해를 설명한다.

## intent — 사용자 의도 반영

- 제공된 요구사항 체크리스트의 각 항목을 구현 위치와 연결한다.
- 정상 경로뿐 아니라 오류·빈 입력·취소·경계조건에서 요구사항을 지키는지 확인한다.
- API 계약, 기본값, 데이터 매핑, 중복·누락 처리, 사용자에게 보이는 동작의 변화를 점검한다.
- 누락과 범위 밖 변경을 구분한다. 요구사항이 모호하면 확인 불가로 표시하고 정책을 창작하지 않는다.
- 모든 요구사항에 반영/누락/확인 불가 상태와 근거를 반환한다.

## tests — 테스트 충분성

- 변경 동작을 실제로 검증하는 테스트와 assertion을 찾는다.
- 바뀐 구현에서 실패해야 할 테스트가 기존 구현에서는 통과하는지, 또는 그 반대인지 검토한다.
- 회귀 가능성이 있는 실패·경계·빈 값·중복·동시성 경로 중 변경에 관련된 것만 살핀다.
- 과도한 mock이나 결과를 확인하지 않는 테스트 때문에 결함이 가려지는지 확인한다.
- 줄 수나 임의의 커버리지 기준으로 판정하지 않는다. 필요한 테스트를 구체적인 입력과
  기대 결과로 제안한다. 단순 문서 수정에는 불필요한 실행 테스트를 요구하지 않는다.
- 읽은 테스트와 실제 실행된 테스트를 구분한다. 테스트 파일을 추가하거나 실행 중 자동 수정하지 않는다.

## performance — 성능

- 변경 전후의 데이터 크기·반복 횟수·복잡도를 비교한다.
- 루프 내부 DB/네트워크/파일 I/O, N+1, 중복 파싱·정렬, 캐시 무효화, 불필요한 복사를 살핀다.
- 메모리 누적, 무제한 큐·병렬 실행, 이벤트 루프 차단, 잠금 경합 등 관련 자원 사용을 점검한다.
- 병목이 발생할 입력 규모와 실행 경로를 제시한다. 작은 상수 비용을 근거 없이 높은 중요도로 매기지 않는다.
- 측정값이 없으면 정적 분석에 따른 가능성임을 밝힌다. 벤치마크 숫자나 개선율을 만들지 않는다.
